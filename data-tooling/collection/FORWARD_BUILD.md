# 正向构建采集方案（v1.4）

> 状态：`proposed`
> 建立日期：2026-11-06
> 决策：**人工在平台上采集标题/简介/tag/评论区，同一次交互内完成标注**；
> **AI 若使用，只做预标注，最终标签由人给出**；评论按最新、最热各取 10 条，不足取全部

本方案与 [README.md](./README.md)（v1.3 标注前置采集）的关系：v1.3 解决「人的观察是权威」，v1.4 在此之上补齐**采集阶段必须固定住的判定用途字段**。**v1.4 的采集主体是人，不是爬虫。**

## 0. 采集方式：人工

标注者直接在平台上打开帖子，把下列内容抄录进 `manual_entry.py`，并在同一次交互内给出最终标签：

| 抄录项 | 说明 |
| --- | --- |
| 链接 | 用于派生 `post_id`，无需爬虫 |
| 作者 ID / 昵称 | 派生 `blogger_id` |
| 标题 | 平台原文 |
| 简介 / 描述 | 与正文分开填 |
| 正文 | B站视频可留空，只填简介 |
| tag | 逗号分隔 |
| 评论区 | 最新、最热各 10 条，不足取全部；行首 `[新]`/`[热]` 标注来源 |
| 判定依据 | 是否看完、披露状态、依据说明 |
| 标签 | 最终标签、置信度、证据码、理由 |

**为什么人工采集能解决根本问题**：披露判定（「披露区域已完整采集」）只有人在平台上能确认。机器采集时 `collection_complete` 全池 100% 为 `None`，判定前提无从记录；人工采集时它天然为 `complete`，52 条暗广那类「前提不可审计」的情况不会再现。

人工抄录的 `post_id` 与既有池完全对齐（已实测：同一条 B站链接派生出 `post_20f869926850b4918f5c9a3b23448fc2`，与池中既有记录一致），因此新旧数据可按需对照。

## 1. 为什么必须人工采集：既有数据的三个硬缺陷

### 1.1 评论实际只采到 3 条

| 评论数 | 帖子数 | 占比 |
| ---: | ---: | ---: |
| 0 | 700 | 23.9% |
| 1 | 12 | 0.4% |
| 2 | 26 | 0.9% |
| **3** | **2,194** | **74.8%** |
| > 3 | **0** | 0% |

在原始采集输出 `data/run_outputs/bilibili_20260728_130630/anonymized_posts.jsonl`（1,517 条）中同样是：984 条恰好 3 条、522 条 0 条、最大 3。**不是下游截断，是采集时就只有 3 条。**

**根因**（已定位到代码）：

```python
# bilibili_crawler.py:1367
session = requests.Session()   # 空 session，无任何 Cookie

# bilibili_crawler.py:877
params={"type": comment_type, "oid": oid, "pn": page, "ps": 20, "sort": 1}
```

Playwright 预热得到的 `storage_state`（含 SESSDATA）只用于抓 HTML，**从未注入 requests.Session**。B站评论接口在匿名状态下只返回 3 条热评，`max_comments=50` 实际无效。

**后果**：S-6「反讽排除」规则要求以评论区佐证（「演」「梗」「太像了」），52 条暗广的判定里评论证据几乎为空。这是一条写在规则里、但没有数据支撑的判据。

### 1.2 tags 从未采集

| 检查项 | 结果 |
| --- | --- |
| schema 有 `tags` 字段 | 无 |
| 爬虫调用 tag 接口 | 无 |
| AI 提示词使用 tag | 无 |
| 现有数据中 `#xxx#` 文本 | 53 条（1.8%），是正文井号，非平台 tag |
| 其中含披露词（广告/赞助/合作） | 0 |

### 1.3 简介与正文混淆

B站视频的 `desc`（简介）被直接塞进 `text`，并混入「视频播放量 151538、弹幕量 819、点赞数 5915……」等页面样板文字。

## 2. 五阶段流程（人工采集版）

```
S1 采集 + 核验（人）   平台上打开帖子，抄录标题/简介/tag/评论，填 intake
S2 预标注（AI，可选）  基于 S1 内容给参考意见
S3 标注（人）          给出最终 label / confidence / evidence_codes
S4 质检                自检告警 + 抽样复核
```

S1 与 S3 在 `manual_entry.py` 里**一次交互完成**：判定所需的证据与标签同时落盘，不会因为后续爬虫失败或链接失效而变成不可复核的记录。

若启用 AI 预标注，必须放在 S1 之后、S3 之前：`disclosure_status` 只有人看平台能填，AI 无从得知；把它放在 AI 之后等于让 AI 猜前提。AI 输出只能进 `pre_annotation`，**不得写入最终 `label`**。

## 3. S1 采集：抄录字段清单

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `post_id` | `sha256(salt+url)[:32]` | 只依赖链接，抄录时即确定 |
| `platform` | 链接匹配 | 自动识别 |
| `blogger_id` | 作者 ID/昵称 + salt | 即 creator_id |
| `title` | 平台原文 | 确实无标题时留 `null`，不得写字符串 `"None"` |
| `desc` | 平台简介 | **与 `text` 分离** |
| `text` | 平台正文 | 剥离播放量等页面样板 |
| `tags` | 平台 tag | 逗号分隔录入 |
| `comments[]` | 见 §4 | 最新/最热各 10 条 |
| `comments_meta` | 见 §4 | 覆盖范围与抄录时点 |
| `stats` | 平台 | 可选，仅供参考，不得单独作为商业意图证据 |
| `media[]` | 平台 | 视频至少记 `source_url` |

**硬性要求**：`title` 为 `null` 与 `title` 为 `"None"` 必须区分。前者是确实没有标题，后者是抓取缺陷。既有 852 条（29.1%）犯了这个错。

## 4. S1 评论抄录：最新 + 最热各 N

N=10，总数不足则取全部。

### 4.1 抄录约定

在平台上分别把评论区切到「最新」和「热门」，各抄 10 条。行首标注来源：

```
[新] 然后莲花破产了 | 42
[热][新] 宣传减重结果3吨 | 18
[热] 产品决策难崩
```

- `[新]` = 来自最新排序
- `[热]` = 来自热门排序
- `[热][新]` 或 `[新热]` = 两个排序里都出现（说明既新又热）
- `| 数字` = 点赞数，可选

同一条评论在两个排序里都出现时只录一次，用双标记表示 —— 这比录两遍更能说明它在两处都靠前。

### 4.2 为什么必须记录来源

只记内容不记排序，无法知道评论是「最新」还是「最热」。这两个排序的信息价值不同：

- 最新：反映此刻观众的第一反应，反讽识别（S-6 的「演」「梗」）常出现在最新
- 最热：反映沉淀后的主流判断

混在一起会掩盖这个差异。

### 4.3 为什么必须记 `collected_at`

评论是活数据，会持续增长。同一帖子在不同时点采集，评论集合不同。不记时点，后续无法复现，也无法判断「当时评论区是否已有反讽识别」。

## 5. AI 预标注：可选，定位与边界

### 5.1 决策

**若使用 AI，只做预标注，最终标签由人工给出。** 输出进 `pre_annotation`，`annotation_method` 记 `human_assisted`。

`auto_accepted` 不得进入 Gold —— 既有 `build_gold_dataset.py` 已明确排除该值。

不使用 AI 时 `annotation_method` 记 `human`，这是本方案当前的默认做法。

### 5.2 给 AI 的输入

`title` + `desc` + `tags` + `comments`（含 `sort_source`），以及 S2 的 `intake.viewed_media` 与 `intake.disclosure_status`。

**不给**：人工的 `draft_label`。否则 AI 只是在复述人的初判，预标注失去独立价值。

### 5.3 输出设计

| 字段 | 说明 |
| --- | --- |
| `label` | 允许 `null` 表示弃答 |
| `confidence` | 0–1 |
| `evidence_text` | **自由文本**，刻意不给结构化证据码 |
| `concerns` | 模型自述的不确定点、需人核实的项 |
| `abstain_reason` | 弃答原因 |
| `input_fields` | 实际喂入的字段名，用于复现 |

**为什么不给 `evidence_codes`**：结构化码一旦由 AI 给出，人工极易照抄，`evidence_codes` 会退化成 AI 的复述，失去人工证据的独立信息量。

### 5.4 必须承认的风险：锚定效应

AI 预标注可见，人的判断会向它靠拢。既有数据无法分离这个效应：

| 分组 | 标注日 | AI 建议 | 暗广率 |
| --- | --- | --- | --- |
| `control[0:120]` | 11-02 | 无 | 5.6%（6/108） |
| `control[120:180]` | 11-03 | 有 | 17.2%（10/58） |
| `assisted[0:324]` | 11-03 | 有 | 11.5%（36/313） |

同池对比差异显著（z=2.43），但**归因不可识别**：既可能是 AI 锚定，也可能是跨日校准漂移；且同为 11-03 的两组不显著（z=−1.22），说明 17.2% 这个点估计受 n=58 影响很大。

**建议的低成本保护**（可选，非必需）：从主池随机抽 10% 做 `annotation_method=human` 的盲标，用来量化预标注的影响。不加这个子集，事后就只能承认"不知道 AI 帮了多少、带偏了多少"，与既有 479 条的困境相同。

## 7. 与既有 479 条 Gold 的关系

**不回溯重建。** 那 479 条的 `disclosure_status`、`viewed_media`、`tags`、评论（仅 3 条）都无法补录 —— 评论会随时间增长，事后补采的评论集与当年不同，补录等于制造虚假可复现性。

处理方式：

- 479 条保留为「v1.0 指南下的历史 Gold」，Dataset Card 标注其局限：评论覆盖不足、披露前提未记录、无 tags
- 新方案产出的数据集单独命名（如 `formal_v2_forward`），不与 479 条混合统计
- 论文中如需合并报告，必须按采集方案分层披露，不能当作同质样本

## 9. 预期收益与已知限制

**收益**

- 披露判定前提首次可记录、可审计（`collection_complete=complete` 由人确认）
- 评论从 3 条提升到约 20 条，S-6 反讽排除规则首次有数据支撑
- tags 可提供商单标识（如 `#商单#`、品牌名），需试点实测出现比例
- 简介与正文分离，AI 输入更准确
- 判定证据与标签同批落盘，链接失效也不影响复核

**限制**

- **不可规模化到数千条**。人工抄录每条约 2–4 分钟，100 条约需 4–7 小时。若目标仍是 1,500 条 Gold，人工采集需约 60–100 小时，须在计划上明确取舍
- `viewed_media=full` 是自述，无法机器验证
- 评论抄录依赖人是否覆盖「最新」和「热门」两个排序，可能漏抄
- 若启用 AI 预标注，锚定效应无法在单批内分离，除非另设盲标子集

## 10. 与爬虫方案的关系

`comment_collector.py` 保留为**可选的规模化路径**：当需要处理大样本时，可用它做机器采集，再由 `manual_entry.py` 的人工判定覆盖。

但要注意两者的证据强度不同：

| 维度 | 人工采集 | 爬虫采集 |
| --- | --- | --- |
| `collection_complete` 可信度 | 高（人确认） | 低（全池曾 100% 为 None） |
| 披露判定前提 | 可审计 | 不可审计 |
| 可规模化 | 否 | 是 |
| 评论覆盖 | 人保证覆盖双排序 | 需登录态，否则只有 3 条 |

**混用两种来源时必须分层标记**（`annotation.collection_mode` 已区分 `manual_platform` / `crawler`），不得合并后当作同质样本统计 —— 这与既有 479 条「批次不可比」是同一类问题。
