# 现有代码修改大纲

> 目的：说明如何从当前P2代码骨架迁移到证据驱动的Agent系统，并把已合并的P1数据资产接入同一主线。  
> 本文是文件级改造大纲，不表示代码已经完成；正式实施时按TDD拆成可独立验收的小任务。  
> 当前基线：`implicit-ad-agent/impad`约1982行；测试18个文件约773行；2026-07-21默认回归 `58 passed, 2 skipped`。

## 1. 改动结论

不需要推倒重写。

- 现有7个工具、VisionContext、视觉缓存和大部分工具测试可以保留。
- `state → graph → agents → judge → app` 主链需要重构。
- P1已有权威JSON Schema，不再新建平行字段标准；代码只增加运行时适配和证据契约。
- MCP、A2A、RAG、CreatorShift、平台适配和Web工作台以新模块为主，尽量不侵入工具核心。

预计规模：

| 类型 | 预计数量 |
| --- | --- |
| 重度修改现有文件 | 6～8个 |
| 中度修改现有文件 | 6～10个 |
| 基本保留的现有文件 | 12～15个 |
| 现有代码语义改动 | 约20%～35% |
| P2.5最小新增生产代码 | 约1500～2500行 |
| 完整P3～P5新增生产代码 | 约3000～5000行 |
| 新增测试代码 | 约1000～2000行 |

完整目标工作量较大，但主要来自新增边界清晰的模块，而不是重写现有视觉和工具实现。

## 3. P1资产需要修改和补验收的地方

### 3.1 候选数据迁移

598条候选记录与v1.0 schema存在结构差异：

| 当前候选字段/格式 | v1.0要求 | 处理方式 |
| --- | --- | --- |
| `post_id` 为裸哈希 | `^post_...$` | 用稳定映射增加前缀，保存ID映射表 |
| `_collected` | `provenance` + `privacy` | 显式迁移；无法确认的字段不伪造 |
| media只有 `ref/source_url/caption/is_content` | `media_id/type/ref/sha256/phash/ocr_text` | 计算可得字段；不可得填null；source URL留受控原始层 |
| 文件名为`.jsonl`但记录跨多行/连续对象 | 一行一个有效JSON对象 | 转换为规范JSONL并增加格式测试 |
| 存在`title` | v1.0没有title | 经评审发布v1.1可选字段，或由适配器并入运行态；不静默放宽v1.0 |
| 平台仅微信公众号 | 目标含小红书/B站 | 后续采集遵循同schema；B站枚举通过v1.1变更 |
| `terms_checked_at`全空 | provenance要求可审计 | 未完成来源核验前不得进入可公开金标 |
| 356条 `llm_needs_review=true` | 内容应人工复核 | 建立复核队列，不把LLM抽取置信度当标签置信度 |

建议新建：

- `scripts/data/migrate_p1_candidates_to_v1.py`：只读旧候选，输出新文件和ID映射。
- `scripts/data/report_p1_migration.py`：输出成功、降级、拒绝记录和字段缺失分布。
- `tests/data/test_migrate_p1_candidates.py`：固定小fixture验证迁移，不加载真实数据。

原始候选数据保持只读，不原地覆盖。

需要复查并按权威schema收口：

- `implicit-ad-agent/scripts/data/run_full_pipeline.py`：最终输出必须由同一个schema写入器生成。
- `implicit-ad-agent/scripts/data/crawl_public_posts.py`：采集结果先写受控raw层，不直接声称已脱敏。

候选数据中可能存在直接来源URL、联系方式、内部地址或疑似秘密字符串。必须增加：

需要复查：

## 4. 现有代码的重度修改

### 4.1 `implicit-ad-agent/impad/state.py`

当前问题：State直接保存松散dict、Agent投票和字符串证据。

修改方向：

- 保留LangGraph State的轻量容器职责；
- `post` 改为标准PostRecord序列化结果；
- 删除以投票为中心的数据流；
- 增加tool results、evidence bundle、capture status、run metadata、review status；
- reducer只做确定性合并，不在State里隐藏业务判断。

### 4.2 `implicit-ad-agent/impad/graph.py`

当前问题：固定串行 `Supervisor → 专家队列 → Judge`。

修改方向：

```text
normalize_input
→ capability_plan
→ function_call/tool_execute
→ evidence_normalize
→ evidence_gate
→ intent/disclosure/creator_shift
→ judge
→ legal_rag
→ report
```

- 独立节点负责单一职责；
- 可并行的工具按模态并行；
- local/A2A通过runtime接口切换，不复制整张图；
- RAG在结论后运行。

### 4.3 `implicit-ad-agent/impad/agents/supervisor.py`

当前问题：只根据有无图片和历史生成固定列表。

修改方向：

- 调用确定性Capability Planner；
- 向LLM只开放合法工具；
- 写入最大调用数、超时、预算和trace；
- 无Key时输出确定性计划；
- 不直接给三元结论。

### 4.4 `implicit-ad-agent/impad/agents/judge.py`

当前问题：固定NLP/视觉/行为权重投票，缺失模态可能被错误稀释。

修改方向：

- 输入改为EvidenceBundle；
- 先运行Evidence Adequacy Gate；
- 分离CommercialIntent与DisclosureEvidence；
- 缺失/跳过不参与负向评分；
- 证据冲突、低置信或采集不完整转需复核；
- 用dev集校准，不在test调阈值；
- 输出结构化VerdictReport，不在本文件拼接长文本。

### 4.5 `implicit-ad-agent/impad/agents/behavior_agent.py`

当前问题：关键词命中率占位规则。

修改方向：

- 先薄适配现有topic drift工具；
- P4时替换为CreatorShiftClient；
- 强制同creator与 `published_at < target_time`；
- 历史不足返回unavailable/skipped；
- 输出历史证据，不直接投暗广票。

### 4.6 `implicit-ad-agent/app.py`

当前问题：输入模型、HTML、图调用和响应拼装集中在一个文件。

修改方向：

- `app.py` 只创建FastAPI和挂载路由；
- Pydantic API schema放到 `impad/api/schemas.py`；
- 分析入口放到 `impad/services/analyze.py`；
- 增加单条、批量、URL预览/确认、run详情和能力接口；
- API与CLI/Web共用同一服务。

## 8. 新接口的最低定义

### 8.1 P1输入适配

```python
def post_record_from_content_record(record: dict) -> PostRecord:
    """Validate a P1 content_record and create a runtime PostRecord."""
```

不合规输入抛出可定位到字段的验证错误；不得静默丢字段。

### 8.2 ToolGateway

```python
class ToolGateway(Protocol):
    def list_tools(self, context: CapabilityContext) -> list[ToolSpec]: ...
    def call(self, name: str, arguments: dict, run: RunContext) -> ToolResult: ...
```

`LocalToolGateway` 与 `MCPToolGateway` 实现同一协议。

### 8.3 Evidence适配

```python
def evidence_from_tool_result(result: ToolResult, post: PostRecord) -> list[EvidenceItem]:
    """Convert one tool result without inventing evidence or hiding limitations."""
```

每个工具有独立映射测试；适配器只转换，不重算模型分数。

### 8.4 分析服务

```python
def analyze_post(post: PostRecord, options: AnalysisOptions) -> VerdictReport:
    """The single entry point shared by API, CLI, Web and batch evaluation."""
```

## 9. MCP、RAG、CreatorShift和A2A的增量接入

### 9.1 MCP（P3）

新增Detection Tool Server和Knowledge Server；不修改7工具核心。测试本地/MCP同输入的ToolResult关键字段一致，并覆盖服务超时和本地回落。

### 9.2 RAG（P3）

新增文档清洗、切块、索引、混合检索、重排、引用守卫和检索评测。RAG节点在Judge后调用；无证据返回空LawEvidence。LightRAG只实现同一LegalRetriever的候选后端。

### 9.3 CreatorShift（P4）

先实现历史view和简单pooling基线，再实现CreatorShift。模型包只接收时间排序、同creator的历史，输出结构化shift evidence；行为Agent只做适配。

### 9.4 A2A（P5）

在 `ExpertClient`/runtime边界增加A2A实现，远程部署ContentEvidence、CreatorShift和ComplianceRAG专家。主图不因A2A重写；本地专家是参考与降级实现。
