# 隐性广告识别项目：系统与研究说明书

> 本说明书定义稳定的项目目标、架构边界、数据流、组件职责、错误处理和验收原则。
> 阶段、日期、Owner与当前状态见《隐性广告识别项目_分阶段计划表.md》和根目录 `HANDOFF.md`。

## 1. 项目定义

本项目构建一个面向社交媒体的证据驱动多智能体系统。系统接收帖子文本、图片、评论、创作者历史或平台URL，输出：

- 明广 / 暗广 / 非广三元判定；
- 置信度和是否需要人工复核；
- 文本、视觉、评论、历史等可回溯证据；
- 数据采集完整性和缺失项；
- 与结论相关的法规和平台规则引用；
- Agent、工具、模型、提示词和版本信息。

系统第一阶段由4名开发者内部使用，最终以GitHub开源网页工程发布。浏览器插件复用同一后端，属于网页端稳定后的冲刺目标。

## 2. 三条主线

### 2.1 研究主线

CreatorShift研究创作者长期内容偏好及目标帖相对历史的纵向变化。创新点不在“使用LangGraph”，而在：

- 严格时间约束下的创作者历史建模；
- 文本、视觉、商业对象与表达方式的纵向偏移；
- 历史信息充分性与不确定性；
- 对单帖多模态和简单历史池化的可验证增益。

### 2.2 Agent工程主线

Function Calling、MCP、A2A与RAG都是正式能力：

- Function Calling负责受限、结构化、可追踪的工具选择。
- MCP负责Agent到工具/知识服务的标准化接入。
- A2A负责独立专家Agent之间的发现、任务和结果交换。
- RAG负责法规、平台规则和判例的可引用检索。

这些能力必须有可靠性、延迟、失败降级和结果一致性测试，而不是只展示“连通”。

### 2.3 产品主线

网页端提供：

- 手工文本/图片输入；
- JSON或批量文件导入；
- 小红书优先、B站其次的平台URL输入；
- 证据画布；
- 创作者变化时间线；
- 法规引用卡片；
- Agent运行轨迹与local/A2A模式对比；
- 采集结果审计和人工修正。

## 3. 标签、证据与运行状态

### 3.1 正式金标

| 标签 | 操作性定义 |
| --- | --- |
| 明广 | 有充分商业推广意图证据，并发现明确广告、赞助、合作、赠送或平台商业标识 |
| 暗广 | 有充分商业推广意图证据；采集信息完整，但未发现明确披露 |
| 非广 | 没有足够证据支持商业推广意图 |

三元标签描述可观察内容，不认定博主是否真实收款、违法或具有特定主观动机。

### 3.2 数据治理与运行状态

- `out_of_scope`：不属于研究范围，如个人二手交易、招聘、公益募集。
- `uncertain`：人工标注阶段证据不足，进入复核池。
- `需复核`：系统运行阶段采集不完整、证据冲突、低置信或关键工具失败。

三者均不作为第四个正式分类标签。

### 3.3 披露证据

披露不单独训练成高成本任务。系统保存轻量 `DisclosureEvidence`：

- 披露文本或平台标记；
- 来源位置、文本span或图像bbox；
- 获取方式和工具版本；
- 采集完整性；
- 是否存在冲突。

“没有发现披露”只有在相关页面区域、正文和图像采集充分时才能支持暗广；否则进入需复核。

## 4. 设计原则

1. **证据优先**：Agent和工具首先产出事实与证据，Judge最后分类。
2. **契约优先**：先稳定输入、证据、结论三份契约，再增加协议、模型和界面。
3. **单一实现**：本地、Function Calling、MCP和A2A不得复制工具业务逻辑。
4. **可降级**：无Key、无网络、无GPU、缺图片、缺历史、工具失败都应有明确状态。
5. **缺失不等于0**：不可用模态不能被当作负向证据参与加权。
6. **检索不污染分类**：RAG在分类后运行，为报告提供引用，不把法规文本当分类证据。
7. **时间泄漏零容忍**：CreatorShift只看目标帖之前的同创作者历史。
8. **研究与工程分离评价**：CreatorShift看预测增益；协议看互操作、可靠性、延迟和成本。
9. **默认离线可测**：默认测试零Key、零联网；真实集成测试显式opt-in。
10. **最小可用产品**：先服务4名开发者的研究工作流，再公开开源。

## 5. 总体架构

```text
┌─────────────────────────────────────────────┐
│ 输入层：手工 / JSON / URL / 浏览器插件       │
└───────────────────┬─────────────────────────┘
                    ▼
          PlatformAdapter + CaptureAudit
                    ▼
             PostRecord / CaptureStatus
                    ▼
        Capability Planner（确定性过滤）
                    ▼
      Supervisor + 受限 Function Calling
             ┌──────┴──────┐
             ▼             ▼
       Local Expert     A2A Expert
          Runtime         Runtime
             └──────┬──────┘
                    ▼
              ToolGateway
             ┌──────┴──────┐
             ▼             ▼
       Local Registry    MCP Client
             │             │
             └──────┬──────┘
                    ▼
    文本 / 视觉 / 评论 / 历史工具与模型
                    ▼
               ToolResult
                    ▼
      EvidenceAdapter → EvidenceBundle
                    ▼
          Evidence Adequacy Gate
                    ▼
 CommercialIntent + DisclosureEvidence + CreatorShift
                    ▼
             Calibrated Judge
                    ▼
       明广 / 暗广 / 非广 / 需复核
                    ▼
       LegalRetriever → LawEvidence
                    ▼
               VerdictReport
                    ▼
         FastAPI → Web / CLI / Plugin
```

默认运行路径是单进程local模式；A2A是同一契约上的分布式模式。两者必须共享输入、证据和输出模型。

## 6. 数据契约

### 6.1 P1权威schema

`data/schema/data_schema_v1.json` 是数据资产的唯一权威字段标准，定义：

- `content_record`；
- `annotation_record`；
- `annotation_supplement_record`；
- media、comment、provenance、privacy及图像分析结构。

原则：

- 内容、主标注和补充标注分离；
- 内容记录不得包含最终人工标签；
- 通过 `post_id`，补充标注再加 `annotator_id` 关联；
- 未知值使用 `null` 或空数组；
- 任何schema变更都必须升版本并保留迁移脚本。

代码不得维护另一套含义不同的字段表。Pydantic运行模型可以增加运行态字段，但必须明确区分“数据集字段”和“本次运行元数据”。

### 6.2 PostRecord

`PostRecord` 是运行时标准输入，由P1 `content_record` 或PlatformAdapter生成。至少包含：

- schema/version、post_id、platform、creator/blogger_id；
- title（若版本允许）、text、published_at；
- media、comments、history references/resolved history；
- provenance、privacy；
- `capture_status` 引用。

PlatformAdapter不得直接返回Agent私有dict。

### 6.3 CaptureStatus

记录采集完整性，而不是推断标签：

- 各模态状态：`complete / partial / missing / not_applicable`；
- 已获取字段和缺失字段；
- 失败原因、采集时间、adapter版本；
- 是否允许判断披露；
- 用户修正记录。

### 6.4 ToolResult

现有工具信封保留四态：

- `ok`：成功且结果可用；
- `degraded`：使用降级实现，结果可用但需标注限制；
- `skipped`：输入不满足条件，不产生正负证据；
- `error`：执行失败，记录错误但不拖垮整图。

每个结果包含tool name/version、score、evidence、warnings、payload和model info；新增run_id、latency和错误分类时不得破坏现有工具核心。

### 6.5 EvidenceItem与EvidenceBundle

`EvidenceItem` 是Judge唯一接受的分析事实，至少包含：

- `evidence_id`、`kind`、`polarity`、`strength`；
- `source_type`、`source_ref`；
- quote/span/bbox/comment_ids/related_post_id之一；
- producer、tool/model/version、status；
- limitations与时间信息。

`EvidenceBundle` 聚合全部证据、工具状态、模态覆盖、冲突和缺失项。Agent投票不能绕过EvidenceBundle直接写最终结论。

### 6.6 VerdictReport

最终报告至少包含：

- verdict、confidence、review_status；
- commercial intent、disclosure evidence；
- evidence bundle摘要与可展开明细；
- capture completeness和missing requirements；
- CreatorShift结果及历史充分性；
- RAG法律/平台规则引用；
- run metadata、运行模式、模型/工具版本、耗时和警告。

## 7. 输入与平台适配

### 7.1 输入方式

L0支持：

- 手工文本、图片、评论、历史输入；
- P1 schema JSON；
- 单条与批量文件。

L1支持：

- 小红书URL；
- B站URL。

浏览器插件只负责从用户当前页面抽取内容并调用API，不在插件中重新实现分类。

### 7.2 PlatformAdapter职责

每个平台适配器只做：

- 获取公开且允许使用的数据；
- 字段归一化和脱敏；
- 解析披露标记、正文、媒体、评论和历史；
- 生成PostRecord与CaptureStatus；
- 对失败字段给出原因。

它不做广告判定，不绕过登录/验证码/访问控制，不隐瞒采集缺失。

### 7.3 URL可行性策略

- 优先使用公开接口、授权导出、用户当前页面或有限只读采集。
- 用缓存fixture保证测试和答辩不依赖平台实时状态。
- URL采集后先显示审计页，用户确认/修正后再分析。
- 适配失败时退化到手工/JSON输入，不能伪造字段。

当前P5.1只实现这套策略的服务边界：URL必须为HTTPS并通过authority、端口、本地/非公网目标和显式host注册校验；预览不运行分类，展示URL移除query/fragment；确认只接受白名单字段、保留适配器控制的审计元数据并记录实际更正。进程内preview通过原子claim保证同一ID只成功分析一次，失败后可重试。默认注册表为空，因此当前工程不会抓取任何真实平台；未来实时适配器仍须在每次DNS解析和重定向后重复公网目标校验。

## 8. Planner与Function Calling

### 8.1 Capability Planner

Planner使用确定性规则检查：

- 是否有正文；
- 是否有可用本地图片；
- 评论数量是否达到工具最低条件；
- 历史数量、时间戳与creator隔离是否有效；
- 模型、Key、GPU、MCP/A2A服务是否可用。

Planner只决定“哪些工具可以开放”，不直接分类。

### 8.2 Function Calling

LLM只能在Planner允许的工具集合中选择，并受以下约束：

- 严格JSON Schema或Pydantic参数校验；
- 最大工具调用数和最大反思轮次；
- 单工具超时、有限重试与总成本预算；
- 禁止同参数无限重复调用；
- 调用、参数、结果摘要、耗时和错误全部记录；
- 无Key或调用失败时保留确定性规则路径。

Function Calling负责工具调用，不强迫所有最终结构化输出都改用同一模型厂商的tool-call格式。现有 `json_mode + 英文字段名 + Pydantic` 可继续作为兼容输出策略。

## 9. 工具层与MCP

### 9.1 工具职责

现有7个工具分别产出分析事实：

- 文本商业意图；
- 情绪/焦虑/紧迫变化；
- OCR与二维码/促销文字；
- 图文关系；
- 品牌/商品/视觉焦点；
- 历史主题漂移；
- 评论异常。

工具不直接决定最终明广/暗广/非广。

### 9.2 ToolGateway

Agent只依赖统一ToolGateway：

```text
ToolGateway
├─ LocalToolGateway → Python registry
└─ MCPToolGateway   → MCP client → MCP server
```

两条路径返回相同ToolResult。MCP失败时可按配置回落本地；回落必须写入run metadata。

### 9.3 MCP服务

第一版只建立：

1. Detection Tool Server：暴露7个检测工具。
2. Knowledge Server：暴露法规/平台规则检索资源与工具。

不为每个工具单独建服务。验收包括工具发现、调用、契约一致性、超时、错误映射和最小权限。

## 10. Agent与A2A

### 10.1 本地专家

建议的领域Agent：

- `ContentEvidenceAgent`：文本、图片、评论和商业对象证据。
- `CreatorShiftAgent`：历史窗口、主题与表达变化。
- `ComplianceRAGAgent`：法规和平台规则检索、引用整理。
- `Supervisor`：规划、调用与状态推进。
- `Judge`：充分性、冲突、校准和最终分类。

无需给每个小工具单独创建Agent，也不把多Agent辩论列为第一版要求。

### 10.2 A2A分布式模式

每个远程专家拥有：

- 可发现的能力描述；
- 明确输入/输出artifact；
- 任务ID、状态和错误；
- 超时、重试、取消和版本；
- 与本地专家相同的EvidenceBundle边界。

A2A验收必须完成一次Supervisor调用至少两个独立远程专家的端到端分析，并比较local/A2A的结果一致性、延迟、通信开销和故障恢复。单进程函数互调不算A2A。

## 11. CreatorShift

### 11.1 输入约束

- 只使用同一creator的历史；
- 所有历史 `published_at < target_time`；
- train/dev/test按creator或更强的content group隔离；
- 无历史或时间戳不可靠时返回unavailable，不返回0分。

### 11.2 最低模型族

1. 无历史单帖基线。
2. 简单历史均值/最大值/EMA池化。
3. CreatorShift时序模型。

特征可包括主题、品牌/产品分布、劝服方式、情绪/焦虑、视觉商品中心度、转化动作和披露行为的时间变化。

### 11.3 输出

- shift score与置信度；
- 历史充分性；
- 最相关/最矛盾的历史片段；
- 使用的窗口与时间范围；
- 限制和缺失项。

CreatorShift只提供历史证据，不因“变化很大”直接判暗广。

当前工程路径使用`keyword_weights_v1`把目标帖和历史文本映射为同一6维确定性特征，默认EMA（`alpha=0.5`）生成`creator_shift_runtime_v1`摘要。充分历史只产生`polarity=neutral`的EvidenceItem；缺目标时间、无历史或短历史保留`unavailable/insufficient`且无数值证据。该路径用于验证接线、泄漏约束和报告契约，不是最终CreatorShift模型。

## 12. Judge与判定流程

### 12.1 Evidence Adequacy Gate

先检查：

- 是否存在可定位证据；
- 关键模态是否缺失；
- 披露区域是否采集完整；
- 工具是否使用降级模型；
- 证据是否冲突；
- CreatorShift历史是否充分。

关键证据不足时输出需复核和缺失项，不强行三分类。

### 12.2 商业意图

商业意图由多源证据聚合：商业对象、劝服/促销、转化动作、视觉商品证据、评论异常和历史偏移。固定手工权重只能作为起步基线，最终应使用验证集校准。

### 12.3 判定规则

```text
商业意图不足
  → 非广

商业意图中等、证据冲突或关键采集不完整
  → 需复核

商业意图充分 + 明确披露证据
  → 明广

商业意图充分 + 未发现披露 + 披露相关采集完整
  → 暗广

商业意图充分 + 未发现披露 + 披露相关采集不完整
  → 需复核
```

## 13. RAG知识层

### 13.1 知识库

- 国家法律法规与部门规章；
- 小红书、B站等平台商业内容/社区规则；
- 经许可的典型案例和解释材料。

每份文档记录来源、版本、发布日期/有效期、抓取日期和权威等级。

### 13.2 检索接口

统一 `LegalRetriever` 返回 `LawEvidence`：

- source_id、document title、article/section；
- quote、source URL/path、retrieval score；
- document version与effective date；
- rerank score和限制。

最终报告只能引用检索结果中实际存在的内容。检索不到时明确返回空证据。

### 13.3 技术路线

- Chroma是第一版基线。
- 可加入关键词+向量混合检索和重排。
- LightRAG只在Chroma稳定后通过同一接口做A/B；不接管CreatorShift历史记忆。

RAG评测至少包括Recall@K、MRR/nDCG、引用正确率、无答案误引率、P95延迟和索引成本。

## 14. API与网页端

### 14.1 API

FastAPI服务层至少提供：

- 单条分析；
- 批量分析；
- URL采集预览/确认；
- run详情与轨迹；
- 健康检查和能力列表。

API调用统一分析服务，不直接操作LangGraph内部节点。

截至P5.2，以上单条、批量、URL预览/确认、run详情、健康和能力接口均已有后端实现；`/workbench`只用这些既有同源接口。这里的“URL接口已实现”只表示安全服务契约可用；没有注册真实小红书/B站适配器，工作台默认必须显示URL未配置并禁用预览，不能据此宣称真实平台能力、团队UAT或M5完成。

### 14.2 研究工作台

P5.2已实现的开发者页面包含：

1. 输入与采集审计。
2. 结论、置信度、复核状态和缺失项。
3. 证据画布：文本span、图像bbox、评论与历史证据。
4. CreatorShift时间线。
5. 法规引用卡片。
6. Agent轨迹、工具状态和local/A2A模式。

实现边界：页面由FastAPI同源提供，无Node构建、远程资产、浏览器存储或后台采集；只有显式点击才复制或下载。未信任值通过文本DOM节点渲染，CSP只允许同源脚本/样式/连接。默认面向开发者，不在第一版加入账号、RBAC、高并发和移动App。

## 15. 错误与降级

| 情况 | 系统行为 |
| --- | --- |
| URL协议、authority、端口或目标不安全 | 在适配器执行前拒绝，返回稳定错误码；不尝试降级抓取 |
| URL host未注册 | fail closed；默认应用不调用网络，提示改用手工/JSON或后续已批准适配器 |
| URL只能获取部分字段 | 展示缺失项，允许修正；披露判断标记未知 |
| 无图片/评论/历史 | 对应工具skipped，不记0分 |
| 模型或Key缺失 | 使用明确标记的规则/轻量模型降级 |
| 单工具错误 | 保留其他证据，生成partial report或需复核 |
| MCP不可用 | 可配置回落LocalToolGateway并记录 |
| A2A专家超时 | 重试有限次数；失败后本地降级或缺失该专家 |
| 证据冲突 | Judge转需复核，不用多数投票掩盖冲突 |
| RAG无可靠证据 | 不生成法规引用 |
| 信息不足 | 拒绝强制分类，列出补充要求 |

## 16. 评估方案

### 16.1 分类与校准

- 三元Macro-F1；
- 暗广Precision、Recall、F1、AUPRC；
- 分类别混淆矩阵；
- AUROC（适用时）；
- ECE、Brier score；
- bootstrap置信区间；
- 需复核覆盖率、已判样本风险和选择性分类曲线。

### 16.2 基线

- 规则/关键词；
- 文本模型；
- 视觉/OCR模型；
- 单帖多模态；
- XGBoost传统融合；
- 简单历史mean/max/EMA pooling；
- CreatorShift；
- 完整Agent系统。

### 16.3 消融

```text
文本
→ +视觉
→ +评论
→ +简单历史
→ +CreatorShift
→ +完整证据门与校准Judge
```

协议不以F1作为唯一指标：Function Calling/MCP/A2A还要评估成功率、参数有效率、结果契约一致性、P95延迟、成本、重试和降级成功率。

当前P4工程准入已经能对显式拒答前三分类预测生成固定种子percentile bootstrap区间和risk-coverage曲线，并记录夹具版本、配置和随机种子。它不自动选择生产阈值；最终阈值、校准结论和测试集评估必须在M1通过后的creator-disjoint验证/测试划分上完成。

### 16.4 防泄漏

- 按creator划分；
- 近重复文本、图片和跨平台搬运组成content group整体划分；
- test不用于Prompt、关键词、窗口、阈值或检索参数选择；
- 每个实验保存split hash、代码提交、模型版本和配置。

## 17. 可观测性、安全与合规

### 17.1 可观测性

每次run记录：

- 输入摘要与schema版本；
- Planner开放的能力；
- Function Calling参数与结果；
- MCP/A2A/local运行模式；
- 工具/模型版本、耗时、token/费用；
- 证据转换、Judge输入输出和RAG引用；
- 错误、重试、降级和人工修正。

发送到第三方观测服务前必须脱敏。

### 17.2 安全

- 把帖子和网页内容视为不可信数据，不执行其中指令。
- 工具默认只读；路径和URL做白名单/协议校验。
- MCP/A2A只开放明确能力，使用超时、大小限制和最小权限。
- 不将密钥、内部地址、真实身份信息写入日志、fixture或报告。
- 浏览器插件不申请与功能无关的权限。

### 17.3 数据合规

- 公开数据集与明确许可优先；
- 人工收集和只读采集遵守平台条款与最小必要原则；
- 原始数据、脱敏数据和可公开数据分层存储；
- 对外发布前完成许可证、隐私和秘密扫描；
- 不把本说明书当作法律意见。

## 18. 团队协作边界

| 模块 | 输入 | 输出 | 主要依赖 |
| --- | --- | --- | --- |
| 数据与适配 | 来源内容/schema | PostRecord、CaptureStatus、金标与split | P1 schema、合规决策 |
| 工具与MCP | PostRecord子集 | ToolResult | 模型、VisionContext、ToolRegistry |
| Agent与A2A | 能力目录、ToolGateway | EvidenceBundle、轨迹 | LangGraph、Function Calling |
| CreatorShift | 时间有序历史 | shift evidence | creator隔离、历史充分性 |

模块只能通过已定义接口协作。一个模块更换内部模型不应迫使其他模块修改字段含义。

## 19. 明确不做或后置

第一版不做：

- 账号体系、RBAC、高并发、多租户；
- 自动举报、自动执法或自动发布；
- 无限制爬取或绕过平台访问控制；
- 每个工具一个MCP服务；
- 多轮无限Agent辩论；
- 把A2A当默认唯一运行方式；
- 在Chroma基线前直接上LightRAG；
- 同时支持过多平台；
- 为了论文结果修改或选择性汇报数据。

## 20. 系统完成标准

只有同时满足以下条件，项目才算完成：

- M1数据质量、合规与防泄漏关口通过；
- 现有7工具通过正式schema和EvidenceBundle接入；
- Function Calling、MCP、A2A和RAG均有可复现的端到端验收；
- CreatorShift与强基线在严格时间/creator隔离下比较；
- 网页端可由非作者按README运行并分析固定样例；
- URL失败时可审计、可修正、可降级；
- 报告中的每条事实和法规引用可回溯；
- 默认测试零Key、零联网，真实集成测试显式opt-in；
- 论文数字、代码、配置、数据split和图表可追溯；
- 开源包不包含无许可内容、个人信息或秘密。

本项目的最终叙事是：**以CreatorShift为研究创新，以证据链为判断核心，以Function Calling、MCP、A2A和RAG构成完整工程，以网页端实现可实际使用与开源落地。**
