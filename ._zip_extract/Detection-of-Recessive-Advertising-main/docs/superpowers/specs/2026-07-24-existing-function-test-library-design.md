# 已有功能测试指令库设计规格

## 1. 目标

在 `docs/已有功能测试指令库.md` 中提供一份面向项目四名开发者的 Windows PowerShell 测试手册。读者应能从激活 `implicit-ad-agent/.venv` 开始，完成所有本地零 Key、零联网功能的必跑验收，并能按需、安全地运行真实视觉和真实 LLM 等可选测试。

文档同时承担教学职责：不仅给出命令，还解释每组测试验证什么、成功输出意味着什么、失败时如何定位，以及相关功能在代码中的数据流和职责边界。

## 2. 安全与范围边界

- 完成依赖安装后，必跑测试路径必须保持零 Key、零联网，不读取或上传真实项目数据；首次安装缺失依赖本身可能访问 Python 包索引。
- 真实视觉、真实 LLM、LangSmith 和其他可能联网、下载模型或产生费用的路径必须集中放在醒目的可选章节。
- 可选路径执行前必须说明前置条件、潜在网络或费用影响、停止方法和成功标准。
- P1 数据资产尚未合入当前分支，因此不把 P1 Schema、采集、标注和数据划分验收冒充为当前可运行功能。
- 当前尚未完成的主图集成、MCP Gateway、真实法规语料、A2A 和网页工作台不得写成已完成测试。
- 命令以仓库根目录 `D:\AAA Jobs\Detection-of-Recessive-Advertising` 为起点，使用 Windows PowerShell。

## 3. 文档组织方式

采用“风险分层主线 + 模块化教学”的混合结构：

1. 先给出环境激活、解释器确认、依赖安装和全量回归的最短主线。
2. 再按功能模块提供可独立执行的专项命令。
3. 之后提供 API、演示程序和 MCP Server 的手工验证方法。
4. 集中列出真实视觉、真实 LLM 与追踪服务等可选测试。
5. 最后提供故障排查、测试结果记录模板和分层学习指南。

## 4. 必跑测试覆盖

必跑章节应覆盖：

- Python 与虚拟环境身份确认；
- 基础依赖以及 `mcp`、`rag` 可选依赖安装；
- `pip check` 依赖一致性；
- `compileall` 语法与导入前置检查；
- 默认全量 `pytest` 回归；
- Agent、API、演示程序和七工具；
- Evidence、Verdict、Run 运行契约；
- Capability Planner、Function Calling、Tool Gateway 和 Tracing；
- Detection MCP 的服务层与真实 stdio 协议测试；
- Chroma 离线法规 RAG、引用守卫和 30 题评估；
- CreatorShift 历史视图、池化基线和偏移解释。

每组命令后均包含：

- 验证目标；
- 当前预期结果；
- 通过标准；
- 失败时的第一检查点；
- 对应源码和测试文件。

## 5. 可选测试覆盖

可选章节使用醒目警告标识并覆盖：

- YOLO/EasyOCR 真实视觉集成；
- 本地图片的真实多智能体演示；
- 使用 `.env` 的真实 LLM 调用；
- LangSmith 等外部追踪；
- 可能下载模型、访问网络或产生 API 费用的行为。

默认“一键验收”不得调用这些命令。

## 6. 教学设计

文档结尾按学习深度分为三层：

### 6.1 必须重点掌握

- 统一 `ToolResult` 和证据语义；
- `skipped/unavailable` 与负向证据的区别；
- Capability Plan、Function Calling、Tool Gateway 的职责分工；
- EvidenceBundle 到 VerdictReport 的证据链；
- 默认测试的零网络隔离原则；
- CreatorShift 的严格时间边界和未来信息泄漏。

上述内容不仅讲代码用法，还必须解释以下理论基础：

- **契约驱动设计**：为什么先稳定输入、输出和错误语义，再替换模型或通信协议；结构兼容与语义兼容有什么区别。
- **证据与不确定性**：证据来源、强度、极性、缺失、冲突和覆盖度如何影响结论；为什么“没有观察到”不等于“观察到不存在”。
- **测试分层与可复现性**：单元测试、契约测试、协议集成测试和端到端测试分别证明什么；为什么确定性、固定 fixture、零网络和显式 opt-in 是科研工程可信度的一部分。
- **工作流与自主 Agent 的边界**：确定性编排、Function Calling、MCP 和 A2A 的能力范围、耦合程度与失败模式。
- **纵向建模与数据泄漏**：时间穿越、同创作者泄漏、分布漂移、历史不足和评价切分为何会让离线指标虚高。

### 6.2 建议部分深入

- Local/MCP 共用工具实现与协议适配；
- Chroma 检索、确定性 embedding、引用守卫和拒答；
- RunMetadata、RunEvent 与可观测性；
- VisionContext 的内容哈希缓存与视觉模型复用；
- Pydantic 契约校验和兼容字段。

部分深入内容必须补充以下理论：

- **信息检索基础**：向量表示、相似度、Top-K、Recall@K、跨文档检索、阈值拒答，以及“检索到相关内容”和“足以支持结论”的区别。
- **引用完整性**：检索结果、原文片段与最终引用之间的可追溯约束；为什么生成模型不能补写未检索到的条款。
- **协议适配理论**：业务能力、传输协议和部署方式三层解耦；Local/MCP 一致性测试为什么比“服务能启动”更重要。
- **多模态证据融合**：文本、图像、OCR、行为和历史模态的条件独立假设为什么通常不成立；缺失模态为何不能简单补零。
- **缓存与幂等性**：内容哈希、工具版本、重复调用和索引替换如何保障同一输入的可重复结果。
- **可观测性**：业务 State、运行 Trace、日志和指标的区别；轨迹为什么应解释执行过程而不改变分类真值。
- **校准与拒绝预测**：置信度不是天然概率；证据不足时返回复核或拒答，通常比强行分类更可靠。

### 6.3 当前只需了解

- LangGraph 现有起步图；
- FastAPI 当前接口；
- 真实 LLM 与 LangSmith 接入；
- 尚未接入的 A2A、网页工作台和 P1 主链适配。

重点主题采用统一教学模板：

1. 它解决什么问题；
2. 背后的核心概念、成立条件和理论假设是什么；
3. 输入、状态和输出如何流动；
4. 对应哪些代码；
5. 哪些测试证明它，哪些性质仍未被当前测试证明；
6. 推荐亲手修改或观察什么；
7. 常见误解和反例是什么；
8. 它与论文实验、工程可靠性和后续架构有什么关系。

理论教学不得变成脱离项目的术语堆砌。每个核心概念至少包含一个项目内例子、一个错误做法、一个对应测试，以及一个可由开发者亲手完成的小实验；涉及指标时给出符号含义、直观解释和当前项目中的实际数值示例。

## 7. 验收标准

完成的测试指令库必须满足：

- 从虚拟环境激活开始，命令可按顺序复制执行；
- 所有路径和命令与当前仓库一致；
- 默认主线不需要 Key、不主动联网；
- 当前默认全量回归预期为 `142 passed, 2 skipped`；
- 真实视觉、LLM 和可能计费功能明确标为可选；
- 每个已完成模块均有独立测试入口和对应代码索引；
- 对尚未完成功能明确说明“当前不可验收”；
- 重点教学同时覆盖理论、代码、测试和实验，且明确“当前测试能证明什么、不能证明什么”；
- 至少实际执行环境检查、依赖检查、编译、全量回归和各新增模块专项测试；
- 文档不存在 `TODO`、`TBD`、占位命令、错误路径或未解释的预期输出。
